## 검증 기록

### 적용 결과

- 전체 목록의 모든 화면과 선택·필터·편집·확인창에 공통 기반을 적용했다. 기존 Material 3 / Riverpod / GoRouter / Drift 구조, 데이터 모델, DB 버전과 서버 API는 유지했다.
- `AppSpacing`, `AppRadius`, `AppLayout`: 여백 스케일, 8/12/16dp 라운딩, 48dp 조작 대상, 읽기 720dp/관리 1200dp 폭, 840dp rail 전환을 명시했다.
- ThemeData에 버튼·아이콘 버튼·입력·Chip·dialog·FAB·ListTile·카드 규칙을 고정했다. 카드 hover/ink도 둥근 경계 밖에 그려지지 않도록 했다.
- `AppPageBar/AppBackButton`: 상세 헤더 왼쪽의 동일 복귀 화살표·tooltip, 최상위에서는 제거. 결과의 홈 목적지 버튼은 별도 홈 아이콘으로 표현했다. 직접 진입 시 시스템 복귀도 상위 목적지로 처리하며 편집 guard를 우회하지 않는다.
- `AppActionGroup/AppDialog`: 가로 동등 행동은 같은 너비·높이, 부족하면 같은 너비의 세로 배열. 긴 라벨·200% 확대를 억지로 한 줄에 자르지 않는다.
- `ConceptBadge`와 의미별 wrapper: 특성 배지의 compact/normal variant, 라운딩·글자·패딩·테두리 규칙을 공통화했다. 개념·문제·AI 검수·필터·동기화 모두 사용한다.
- `ReviewStatusBadge`: 개념 검토 완료와 문제 승인 완료를 같은 표면·테두리·완료 색으로 표시한다. 개념의 검토/문제의 승인이라는 업무별 라벨만 유지하며 화면별 임의의 완료 색은 없다.
- `AppOptionSelector`와 `questionTypeOptions`: 단일 선택은 충분한 폭에서 segmented, 좁을 때 줄바꿈; 다중 선택은 공통 FilterChip. O/X→객관식→단답형→서술형 및 아이콘이 모든 문제 유형 입력에서 같다.
- 홈은 학습 시작을 첫 행동으로 올렸고, 자료의 제목 중복을 없앴다. 섹션 제목은 titleMedium, 카드 내부 여백은 16dp로 정리했다.

Computer Use로 네이티브 Release 앱을 실행했다. 사용자 앱과 DB를 건드리지 않도록 `tool/ui_preview.dart`의 메모리 DB, 합성 자료, 가짜 API/설정/키 저장소를 사용했다. 실제 유료 API·서버 시작·사용자 자료 삭제는 수행하지 않았다.

### 자동 검증

- 전체 기존 테스트를 유지했다. 새로운 화면 검증은 360/720/1280dp × 글자 100/200% × 라이트/다크의 12조건에서 22개 GoRouter 목적지 및 OCR 편집/읽기 전용을 렌더링·스크롤·접기한다. 좁은 폭은 Android, 넓은 폭은 Windows 플랫폼으로 테스트했다.
- 동등 행동/배지 치수, 모델/추론 입력 테두리 높이를 실측한다. 추가 테스트는 키보드 인셋·저장 버튼 접근, 직접 진입 헤더/시스템 복귀와 입력 보존, 확대된 삭제 확인 취소, 지연 승인 중 같은 프레임 중복 제출 차단을 다룬다.
- 발견한 회귀를 수정하고 재검증했다: 선택 헤더 overflow, 난이도 dropdown 폭, 서버 상태 행 overflow, dialog intrinsic LayoutBuilder 충돌, 작은 클릭 영역, 키보드 스크롤 후 저장 버튼 미탭, 테스트 Provider/타이머 정리 문제.
- 기존 오류·재시도·동기화·PDF 작업·LLM 자동 저장·검수·선택 필터·이탈 보호·퀴즈 유형/점수 테스트를 전체 실행한다. 새 테스트를 이유로 기존 기능 검증을 제거하지 않았다.
- `flutter analyze`: 오류·경고 없음. `flutter test`: 전체 587개 성공(기존 571개 + 신규 16개).
- `flutter build windows --release` 및 `flutter build apk --debug`: 성공. Windows는 최종적으로 검증용 진입점이 아닌 기본 `lib/main.dart`로 빌드했다. 마지막 공통 완료 배지까지 반영한 코드로 분석/587개 테스트/두 빌드를 재실행해 성공을 확인했다.
- 실행 검증에서 수정한 모델/추론 테두리 높이와 유효한 합성 OCR 이미지도 최신 Windows 빌드에서 다시 확인했다. 연결된 문제 화면의 공통 검색/필터 및 빈 상태 진입도 직접 확인했다.
- PDF 진행 작업 패널의 마지막 840dp 폭 예외를 읽기 720dp로 정리하고 작업 버튼도 공통 그룹으로 묶었다. 큰 O/X 답안 버튼의 크기는 유지하되 모서리는 다른 답안과 동일한 공통 control radius를 사용한다.

### 유지한 구조와 의도한 차이

- Windows의 문제/개념 목록은 기존 사용자의 명시적 요청과 AXTree 우회 구현에 따라 eager 구성과 카드별 로컬 펼침 상태를 유지한다. 단순 UI 리팩터링을 위해 lazy 목록이나 상태 관리 체계를 재도입하지 않았다. 향후 대량 목록 성능은 별도 과제다.
- OCR 원문 대조의 좌우 연속 스크롤·페이지 로딩, PDF 작업 지속·재시도, 승인/개념/문제 연결, 프로필 자동 저장 로직은 이미 해당 과업을 수행하므로 바꾸지 않았다. 공통 헤더·테마·반응형 조작을 확장하고 회귀 테스트로 확인했다.
- 최상위 모바일 bottom navigation / 넓은 rail, compact 목록 배지 / 펼친 본문 배지, 단일/다중 선택의 형태 차이는 공통 컴포넌트에 조건을 명시한 변형이다. 카드와 읽기 영역의 최대 폭 차이는 관리/읽기 목적에 따른 것이다.
- 기존 라우팅의 두 계열도 유지한다. 탐색/설정은 Shell의 주요 목적지 내비게이션을 유지하고, 편집·생성·풀이·원문 비교는 작업에 집중하는 전체 화면이다. 두 계열 모두 현재 콘텐츠 헤더의 왼쪽 같은 AppBackButton을 사용하며 부모 화면으로 복귀한다.
- 생성 단계의 문제 삭제는 내부 기존 reject 동작을 유지하면서 화면 표현만 일반 삭제와 통일했다. 저장·삭제·분류 모델/마이그레이션을 변경하지 않았다.

### 미검증과 재현 절차

1. 실제 Android 기기의 터치/키보드/IME/TalkBack: `flutter run -d <Android 기기>` 후 자료·문제 편집과 서술형 답안, 200% 글자 크기, 유형 선택·뒤로가기·dialog를 확인한다. APK 컴파일 및 Android 위젯 테스트는 실기기 확인을 대체하지 않는다.
2. Windows Narrator 전체 읽기/키보드 순서·한국어 IME: 실제 앱에서 Tab/Shift+Tab/Enter/Space 및 한국어 장문 입력, 접힌 카드/배지 토글을 확인한다. tooltip/Semantics와 대비는 테스트로 확인했으나 스크린리더 실사용을 완료했다고 보고하지 않는다.
3. 실제 PDF 원본 내용 대조·업로드·OCR 편집/확정·실제 API 실패/재시도·서버 시작/종료: 테스트 저장소/서버에서 실제 파일로 확인한다. 사용자 DB와 API 비용을 보존하기 위해 이번 네이티브 조작은 격리 구현을 사용했다.
4. `desktop_drop` Android Kotlin Gradle Plugin 호환성 사전 경고는 기존 의존성에서 발생한다. 이번 UI 변경으로 빌드가 실패한 것은 아니며 무관한 의존성 업그레이드는 하지 않았다.
